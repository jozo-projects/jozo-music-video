# Video device approval

The gate reads `GET /room-device-authorization/config` from `VITE_API_BASE_URL`. Only a valid `{ "enabled": false }` disables it; the default and any failed or malformed lookup enable the gate. Configuration is refreshed every 30 seconds and on window focus, without a rebuild. Roomless playback, including standalone HLS, is unchanged. A room with the gate enabled waits for approval before mounting the player.

Explicitly configure absolute `VITE_API_BASE_URL` and `VITE_SOCKET_URL`; they may use different origins and ports from the page. Only those configured destinations receive the proof. HTTPS is required except for localhost and private/LAN IPv4 or `.local` addresses, where HTTP is supported for local testing and exposes traffic to the network. Use TLS in production. Browsers require a secure context (HTTPS or localhost) for `crypto.getRandomValues`; a plain HTTP LAN page may not work. Cross-origin API requests require backend CORS including the proof header. Authenticated Socket.IO uses WebSocket only to avoid redirect forwarding, so the server/proxy must support WebSocket. Proof-bearing HTTP requests reject redirects. The proof is stored in localStorage per room; clearing site data loses it. Browser scripts on the same origin can access it, so protect that origin against XSS.

Pending and approved requests are checked every 30 seconds and on socket events. Transient failures retry without creating a new proof. Expired/revoked requests trigger a new request; rejected requests remain rejected. Approval remains active during a status failure, but an observed revocation unmounts the player. This is a client-side gate only: it does not establish or assert backend enforcement.
